## 1. Confirmed findings and unresolved hypotheses

No confirmed P0/P1/P2 product-code finding. Two P3 evidence-description corrections are concrete:

- `/private/tmp/arcium-pip-core-pr-body.md:1` says a two-second renderer grace period. `C:2198-2199` starts `automatic_pip_grace_timer_` with `base::Seconds(3)`. Searching the selected patch directories found no later replacement of this timer constant. Correct the body to three seconds. This does not justify changing working source to match stale prose.
- `docs/automatic-picture-in-picture-controls-validation.md:142-148` calls the port-zero launch the strongest captured “cause.” The same paragraph acknowledges an incomplete return control. Say “strongest captured correlation” or “leading launch-condition hypothesis.” The core PR body already uses the appropriately limited wording. Neither that experiment nor the later passing scalar run resolves the intermittent complaint.

Resize first mouse is a real source omission, but its effect on this exact window remains unproved. `ArciumPiPResizeView` subclasses `NSView` and implements down/drag/up without `acceptsFirstMouse:` at `N:512-545`. Apple documents that the default NSView implementation returns false and that accepting first mouse enables click-through in an inactive window. The slider explicitly returns YES at `N:493-495`; buttons and the overlay also opt in at `N:444-446` and `N:1049-1051`. [Apple NSView contract](https://developer.apple.com/documentation/appkit/nsview/acceptsfirstmouse%28for%3A%29).

However, this is not an ordinary activating NSWindow configuration. `N:1921-1942` calls `setActivationIndependence:YES`. In the exact base, `components/remote_cocoa/app_shim/native_widget_mac_nswindow.mm:476-492` makes `_isNonactivatingPanel` return YES, and `:680-686` stores the policy. Key-window eligibility remains a separate host query at `:514-520`; `ui/views/cocoa/native_widget_mac_ns_window_host.mm:1666-1670` answers from Widget::CanActivate. The frameless subclass does not supply an alternative mouse-dispatch implementation. Neither these methods nor the generic Apple contract establishes which first-click branch the recorded CUA gesture actually took. Nonactivation of the owning app must not be equated with proof that every child receives its first mouse-down.

The ancestor override does not make the resize view inherit its method. `N:1023-1047` returns the actual visible child control. Base `bridged_content_view.mm:289-316` traverses native children after the host's classification, while its own first-mouse override at `:791-796` applies to that bridge view. Thus the grip's omission deserves a focused check. It is not established as the cause of the recorded no-op, and cannot explain the slider's no-op because the slider already accepts first mouse.

No common native event-routing defect was identified:

- Native mode returns HTCLIENT at `N:2235-2243` and attaches a registered NativeViewHost at `N:2419-2434`. Base `native_widget_mac_nswindow.mm:557-653` forwards ordinary events to AppKit after redispatch/modal/menu checks. There is no added unconditional drag suppression in these paths.
- `N:496-509` brackets the slider's normal `[super mouseDown:event]` tracking; `N:810-825` makes it continuous. The custom event monitor at `N:693-706` handles scroll wheels only.
- Resize at `N:1452-1477` depends on delivered down/drag/up callbacks and samples `NSEvent.mouseLocation`. Global-pointer sampling is not inherently wrong for resizing a moving window. It can disagree with a synthesized event's coordinates, but the evidence contains no callback/global-coordinate trace proving such disagreement here.
- Chromium also has capture and general event-monitor machinery. Base `native_widget_ns_window_bridge.mm:1054-1078,1080-1118` and `mouse_capture.mm:73-118` can intercept events when enabled. The PiP patch does not establish that a capture owner or consuming general monitor was active during these attempts. Their existence alone is not a bug finding.
- `N:3526-3557` manually begins seeking, sets a value and sends an action. That test checks transport invariance and host lifecycle, not AppKit thumb tracking. The neighboring hidden hit-target test explicitly uses an accessibility press because a hidden window cannot prove physical delivery.

I do not require an unproven first-mouse/global-pointer/capture change before draft review. A small grip override returning YES is a defensible explicit click-through policy, but it must not be represented as a demonstrated fix for these failures. If the next trace shows the inactive grip loses mouse-down at the first-mouse gate, that override is the narrowly justified fix. If down/drag callbacks arrive with changing event positions but a stationary global pointer, repair coordinate sampling using event positions converted to a stable screen coordinate system. Do neither as an automation workaround without distinguishing those cases.

The next useful drag discriminant is one real pointer thumb drag and one grip drag on the existing paused candidate during an authorized idle interval, starting with another app foreground.
